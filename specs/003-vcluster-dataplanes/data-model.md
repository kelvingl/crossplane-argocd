# Phase 1 Data Model: vcluster-Based Dataplane Clusters

## DataPlane (claim) / XDataPlane (XRD)

Redefined by this feature. Represents a single dataplane/spoke *cluster* — not a
workload inside one (that meaning, from feature 001, is retired).

| Field | Type | Required | Notes |
|---|---|---|---|
| `metadata.name` | string | yes (k8s-native) | Becomes the vcluster's Helm release name **and** its namespace inside the hub. MUST be unique — a second claim with the same name is rejected by Kubernetes name uniqueness, satisfying the spec's naming-collision edge case without extra logic. |
| `spec.parameters.kubernetesVersion` | string | no | Passed through to the vcluster chart if set; otherwise the chart's own default is used. |

**Composed resources** (via `compositions/dataplane-cluster/chart`'s
`composition-dataplane-cluster.yaml`, classic Patch-and-Transform):

1. A `provider-helm` `Release` — installs the `loft-sh/vcluster` chart, release name
   and target namespace both set to the claim's name, values overriding
   `exportKubeConfig.server` to the in-cluster Service DNS name (see research.md #2).

**Status/Readiness**: `Ready: True` once the `Release` reports successful
installation (provider-helm's own readiness semantics — unlike feature 002's
`provider-kubernetes` `Object`s, `provider-helm` `Release`s have native readiness
tracking, so no explicit `Ready` patch is needed in the Composition).

**Lifecycle**: Deleting the claim deletes the composed `Release`, which uninstalls
the vcluster's Helm release — its namespace and all resources inside it (including
its kubeconfig Secret) are removed. A separate manual step (unchanged from today)
removes the now-stale `ProviderConfig`/ArgoCD Cluster Secret that pointed at it.

## vcluster (external resource, not a Crossplane-managed type)

The virtual Kubernetes cluster instance created by the `Release` above. Not
represented as its own Crossplane resource — it is the *effect* of the `Release`
being applied, observed via the running pods/Service/Secret inside its namespace.

| Property | Value |
|---|---|
| Namespace (in hub) | Same as the `DataPlane` claim's name |
| Kubeconfig Secret | Auto-generated by the vcluster chart inside that namespace (exact name per research.md #4) |
| API server address | `https://<name>.<name>.svc.cluster.local:443` (in-cluster Service DNS) |

## dataplanes/<spoke>.yaml (unchanged shape, one new consumer)

No schema change from ADR-029's design. The existing `cluster`, `charts`, and
`compositions` fields are untouched. What changes is that the wrapper chart
(`charts/dataplane-cluster` in the platform repo) now *also* emits a `DataPlane`
claim named `{{ .Values.cluster }}` for every file, in addition to its existing
per-entry children.

```yaml
cluster: spoke-01      # now ALSO becomes a DataPlane claim name, in addition to
                        # everything it already meant (ArgoCD Cluster name, spoke
                        # identity for charts:/compositions: entries)
charts: [...]           # unchanged
compositions: [...]     # unchanged
```

## ProviderConfig (provider-kubernetes, per spoke) — unchanged schema, new source

```yaml
apiVersion: kubernetes.crossplane.io/v1alpha1
kind: ProviderConfig
metadata:
  name: spoke-01
spec:
  credentials:
    source: Secret
    secretRef:
      namespace: spoke-01        # CHANGED: the spoke's own namespace in the hub,
      name: vc-spoke-01          # not crossplane-system      (exact name per research #4)
      key: config                # CHANGED: whatever key the vcluster chart uses,
                                  # not the "kubeconfig" key scripts/03 used to write
```

## ProviderConfig (provider-helm, single, hub-wide)

```yaml
apiVersion: helm.crossplane.io/v1beta1
kind: ProviderConfig
metadata:
  name: hub
spec:
  credentials:
    source: InjectedIdentity   # manages Helm releases in the same cluster
                                # provider-helm's own pod runs in (the hub)
```
